# 0032. 토큰 폐기 이후 Access의 발급 초는 폐기 초보다 커야 한다

> 상태: ✅ 확정 · 결정일 2026-11-24 · 결정한 사람: 회원 담당 (#546)
> 대체: - · 대체됨: - · 보완: [0022](0022-token-revocation-and-retry.md) · [0028](0028-member-withdrawal-kakao-unlink-policy.md)

## 배경

[ADR 0022](0022-token-revocation-and-retry.md)는 Access의 `iat`와 끊은 시각을 초 단위로 맞추고 Gateway가 `iat <= 끊은 시각`인 Access를 거절하도록 했습니다.

이 규칙에서는 폐기 직후 같은 초에 정상 발급한 Access도 거절됩니다(0022 「고른 이유」, [0028](0028-member-withdrawal-kakao-unlink-policy.md) 「영향」의 재연결 항목). 비밀번호를 바꾸고 바로 다시 로그인하거나 카카오 연결 해제 직후 다시 로그인하면 방금 받은 Access로 401을 받을 수 있었습니다.

## 결정

Gateway 비교 규칙은 그대로 유지하고, 발급하는 쪽에서 Access의 발급 초가 해당 회원의 최근 폐기 초보다 크도록 보장합니다. 0022 · 0028에 기록된 같은 초 발급 거절 문제는 이 결정으로 해소합니다.

| 항목 | 내용 |
|---|---|
| 발급 조건 | DB 현재 시각의 초가 해당 회원의 가장 늦은 폐기 시각의 초보다 클 때만 발급. 로컬 로그인 · 기존 회원의 소셜 로그인 · 재발급은 같은 확인(`AccessIssueTimeGuard`)을 거침 |
| 끊은 시각을 읽는 곳 | `MEMBER_TOKEN_REVOCATION`의 가장 늦은 `cutoff_at`. 상태와 관계없이 조회함. `PENDING`도 재처리를 통해 나중에 Redis에 기록될 수 있음 |
| 트랜잭션 경계 | `TransactionTemplate`으로 각 시도를 실행. 회원 행 잠금을 획득한 상태에서 발급 시각을 확인함 |
| 발급 조건 미충족 | DB 현재 초가 폐기 초 이하이면 트랜잭션을 롤백해 회원 행 잠금을 풀고, 트랜잭션 밖에서 대기한 뒤 처음부터 다시 실행. 회원 상태 · 인증 정보 · 인증 버전 · 최근 폐기 시각을 다시 확인함 |
| 대기 시간 | 폐기 초의 다음 초까지 남은 시간. 한 번에 최대 1초. 밀리초 변환 시 정밀도 손실로 너무 일찍 재시도하지 않도록 보정 |
| 시도 횟수 | 최초 시도 포함 최대 2회. 두 번째에도 발급 조건을 충족하지 못하면 `MEMBER_BUSY` |
| 재시도 대상 | 발급 시각 조건 미충족을 나타내는 내부 전용 예외만 재시도. 그 밖의 예외는 그대로 전달 |
| 인터럽트 | 대기 중 인터럽트 발생 시 인터럽트 상태를 복원하고 `MEMBER_BUSY`로 종료 |
| 실패 응답 | 로컬 로그인 · 재발급은 409 `MEMBER_BUSY`, 소셜 로그인은 기존 오류 리다이렉트 방식으로 처리 |
| 발급 시각 확인 뒤에 하는 일 | 재발급의 Refresh 소비, 소셜 로그인의 미처리 수신 기록 무효화 · `ACTIVE` 복구, 새 Refresh 저장. 발급 조건을 충족하지 못한 시도에서는 실행하지 않음 |
| 그대로 두는 것 | Gateway 비교 규칙(`iat <= 끊은 시각`), DB `clock_timestamp()`. `iat`는 읽은 DB 시각 그대로이며 임의로 조정하지 않음 |

신규 소셜 회원가입은 새로 생성된 회원에게 기존 폐기 기록이 없으므로 가드 적용 대상에서 제외합니다.

## 고른 이유

- Gateway 비교 규칙을 유지하므로 Redis에 폐기 시각이 기록된 이후에는 기존 Access의 거절 조건이 유지됩니다.
- 잠금 밖에서 기다리므로 그동안 같은 회원의 다른 요청을 막거나 해당 트랜잭션의 DB 연결을 점유하지 않습니다.
- 처음부터 다시 실행하므로 기다리는 동안 일어난 추가 폐기 · 탈퇴를 다시 확인할 수 있습니다.
- 재발급에도 같은 확인을 둡니다. 로그인이 폐기 초보다 뒤에 발급되면 재발급에서 같은 초 문제가 발생하지 않지만, 다른 발급 경로의 동작에 의존하지 않고 재발급 자체에서도 발급 조건을 보장합니다.
- 시도 2회는 회원 잠금 대기 3초 × 2와 발급 시각 대기 1초를 더한 7초를 기준으로 정했습니다. Gateway 기본 응답 타임아웃 10초보다 짧게 잡은 값이며, 이 7초는 두 대기의 상한을 합산한 것으로 전체 응답 시간을 보장하지는 않습니다.

## 다른 안

| 안 | 버린 이유 |
|---|---|
| Gateway 규칙을 `iat < 끊은 시각`으로 변경 | 폐기보다 먼저 발급됐지만 폐기 시각과 같은 초인 Access가 통과함 |
| `iat`를 다음 초로 기록하고 바로 발급 | 실제 발급 시각과 다른 값을 토큰에 기록하게 됨 |
| 회원 잠금을 쥔 채 대기 | 대기하는 동안 같은 회원의 다른 요청을 막고 DB 연결을 점유함 |
| 재발급은 그대로 둠 | 재발급의 보장이 다른 발급 경로의 동작에 의존하게 됨 |
| 시도 3회 | 잠금 대기와 발급 시각 대기의 상한을 합산하면 11초로 Gateway 기본 응답 타임아웃 10초를 넘음 |

## 영향

[인증 규칙](../conventions/auth.md#토큰-폐기), [탈퇴 흐름](../flows/signup-and-replica.md#재로그인), [member 서비스](../services/member.md), [외부 API](../reference/external-apis.md), [시나리오](../testing/scenarios.md) S-A08 · S-B11.

- 재발급은 회원 상태 · 인증 버전 및 발급 시각을 Refresh 소비 전에 확인합니다. 해당 확인에서 실패하면 Refresh를 소비하지 않습니다. 유효하지 않은 상태 · 인증 버전으로 인한 거절 응답은 기존과 동일하며, 남은 Refresh는 폐기 과정에서 삭제되거나 TTL에 따라 만료됩니다. 실제로 꺼낸 Refresh의 회원 · 인증 버전에 대한 최종 확인은 유지합니다.
- 발급 시각 확인 실패 또는 대기 중 인터럽트로 `MEMBER_BUSY`가 발생할 수 있습니다.
- 로그인 · 소셜 로그인 · 재발급 시 최근 폐기 시각을 조회하는 DB 쿼리가 추가됩니다.
- 폐기 기록이 `PENDING`인 동안 기존 Access가 통과할 수 있는 ADR 0022의 한계는 변경하지 않습니다.
