# 0023. 결제 시도 상태를 먼저 커밋하고, 주문 행 잠금을 쥔 채 결제를 부른다

> 상태: 🟨 제안 · 작성일 2026-11-16 · 제안: 주문 · 결제 담당 (Q41)
> 대체: - · 대체됨: -

## 배경

`OrderService.create()`는 주문 저장 · 상품 예약 · 결제 · 결제 완료 처리를 한 트랜잭션에서 했습니다. payment는 자기 DB에 따로 커밋하므로, 결제 직후 market에서 오류가 나면 주문은 롤백되고 차감만 남았습니다. orderId도 함께 사라져 복구할 대상조차 남지 않았습니다.

`repayment()`는 주문 행을 잠근 채 결제를 불렀습니다. 그런데 결제 도중 파드가 죽으면 「결제를 시도했다」는 기록이 없어서, 10분 뒤 만료 스케줄러가 결과를 모르는 주문을 만료 · 예약 해제했습니다. 결과를 모르는 주문은 만료하지 않고 Saga 복구가 확인한다는 정책(노션 4.4 · 11.5, #281)을 지킬 수 없었습니다.

## 결정

첫 주문 생성(`create()`)은 아래 TX1·TX2·TX3로 나눕니다. 재결제(`repayment()`)는 이미 커밋된 주문을 사용하므로 **TX1과 상품 예약을 반복하지 않고 TX2·TX3만 실행**합니다. 전체를 감싸는 트랜잭션은 두지 않습니다.

1. TX1: 주문 · 주문상품 저장 후 커밋 (orderId 확보)
   - 트랜잭션 밖에서 상품 예약 REST. 확정 실패 · 응답 타임아웃이면 다시 부르지 않고 주문 실패 + `market.order-failed.v1` Outbox 커밋 (정책 3.10)
2. TX2: 주문 행 잠금 → 진입 조건(`status = PAYMENT_PENDING` · `paymentState = READY` · `createdAt + 10분` 이내) 확인 → `IN_PROGRESS` 및 `attempted_at`(DB 시각) 커밋 후 잠금 해제
   - 10분이 지났으면 `PAYMENT_WINDOW_EXPIRED`, `paymentState`가 `IN_PROGRESS` · `REVIEW_REQUIRED`이면 409 `PAYMENT_IN_PROGRESS`로 거절하고 payment를 호출하지 않음
3. TX3: 주문 행 잠금 → `IN_PROGRESS` 재확인 → **잠금을 쥔 채** payment REST → 결과 처리 후 커밋. 이미 다른 경로가 처리했다면 payment REST를 호출하지 않음

결제 시도 상태(`READY` · `IN_PROGRESS` · `REVIEW_REQUIRED`)는 주문 상태(`PAYMENT_PENDING`)와 별도 칸입니다. 신규 주문은 `READY`로 초기화합니다. 결과 처리는 다음과 같습니다.

| payment 응답 | TX3에서 커밋 |
|---|---|
| `PAID` · `ALREADY_PAID` | 기존 `orderPayment()` 전체(주문 PAID 전환, `market.order-paid.v1` · `SellerOrderPaid` Outbox, 현행 배송 관련 로직) 실행 후 커밋. Saga 복구도 동일한 완료 경로 사용 |
| 잔액 부족 | `READY`로 되돌림 (10분 지나면 만료 스케줄러가 정리) |
| 확정 실패 (지갑 없음 · 연결 실패 · 4xx) | 주문 실패 + `market.order-failed.v1` Outbox, 장바구니 유지 |
| 결과 불명 (응답 타임아웃 · 5xx) | `IN_PROGRESS` 유지 → Saga 복구. 복구 요청에서 다시 결과 불명이면 `retry_count` 증가, `attempted_at` 갱신 후 커밋 |

Saga 복구 호출에서는 연결 실패도 결과 불명으로 봅니다. 이번 요청이 도착하지 않았을 뿐 원래 요청의 결과는 여전히 모르기 때문입니다. 복구에서 주문을 실패로 끝내는 것은 payment가 판단해 돌려준 응답(지갑 없음 등 4xx)뿐입니다.

만료 스케줄러는 `paymentState = READY`인 결제 대기 주문만 만료합니다. `IN_PROGRESS` 및 `REVIEW_REQUIRED` 주문은 자동 만료하지 않습니다.

Saga 복구 스케줄러는 1분 주기로, **`IN_PROGRESS`이고 `attempted_at`이 10초 이상 지난 주문**을 후보로 찾은 뒤 `FOR UPDATE SKIP LOCKED`로 잠금이 잡힌 주문만 처리합니다. 10초는 제안된 유예값이며 구현·팀 합의에서 최종 확정합니다. 잠금 획득 후 상태를 재확인하고 같은 `orderId`로 결제를 다시 부릅니다. 복구 시 `attempted_at`을 DB 시각으로 갱신하며, 결과 불명이면 `retry_count`를 커밋합니다. **복구 5회 실패 시** `REVIEW_REQUIRED`로 전환하고 팀 알림을 보냅니다. 최초 결제 호출은 복구 5회에 포함하지 않는 설계로 명시합니다.

`attempted_at`의 기록과 조회 시각 비교는 동일한 DB 시각을 사용합니다. 예: 저장 시 `now()`, 조회 시 `now() - interval '10 seconds'`. 결과 불명 예외 때문에 TX가 롤백되어 `retry_count`와 `attempted_at` 갱신이 사라지지 않도록 합니다.

## 고른 이유

- 시도 상태를 먼저 커밋하므로 결제 도중 파드가 죽거나 TX3 커밋이 실패해도 Saga 복구가 그 주문을 찾습니다.
- 내부 REST 정책은 연결 1초 · 응답 3초, 연결 실패만 0.2초 후 1회 재시도입니다. 대표적인 연결 실패 후 재호출 경로는 약 5.2초까지 걸릴 수 있으나, 전체 트랜잭션 시간에 대한 절대 상한은 아닙니다.
- 결제 중 같은 주문을 건드리는 건 구매자 본인과 스케줄러뿐이고, 스케줄러는 SKIP LOCKED라 기다리지 않습니다. market 커넥션은 파드당 10개(Hikari 기본)라 결제가 동시에 그만큼 몰려야 다른 요청이 밀립니다.
- 주문 잠금은 동시 결제 요청과 Saga 복구의 충돌을 줄여 줍니다. 다만 **TX2 커밋 직후부터 TX3 잠금을 다시 얻기 전까지 잠금이 풀린 틈**이 있으므로, 잠금 가능 여부만으로 원래 요청이 멈췄다고 단정할 수 없습니다. 복구는 `attempted_at` 유예 시간과 `SKIP LOCKED`를 함께 적용하고, TX3에서 상태를 재확인합니다. 동일 orderId 멱등 처리도 필수입니다.
- market의 기존 방식(`findLockedById`, 주문 → 판매자 주문 잠금 순서)과 같습니다.

## 다른 안

| 안 | 버린 이유 |
|---|---|
| 잠금을 쥔 채 결제, 시도 상태 기록 없음 (기존 `repayment()`) | 파드가 죽으면 기록이 사라져 결과 불명 주문이 만료됨 |
| 시도 상태를 커밋한 뒤 잠금 없이 결제 (B안) | 결제를 기다리는 동안 잠금 · 커넥션을 쥐지 않지만, 결제 시작 · 완료 · 잔액 부족 되돌리기마다 조건부 UPDATE를 직접 맞춰야 하고, 멈춘 `IN_PROGRESS`를 시간 규칙으로 판별해야 함. 지금 호출 시간 · 트래픽에서는 얻는 것보다 버그 여지가 큼 |
| 결제 조회 API로 결과 확인 | 정책 4.4에서 기각 (조회가 「없음」이어도 늦게 처리된 요청이 차감할 수 있음) |

## B안으로 바꿀 조건

아래 중 하나가 생기면 잠금을 쥐는 비용이 커지므로 다시 검토합니다. 시도 상태 칸과 Saga 복구는 그대로 쓰고, TX3의 REST를 트랜잭션 밖으로 빼고 잠금 대신 조건부 UPDATE를 쓰면 됩니다.

- 주문 결제에서 외부 PG를 직접 부를 때 (응답이 수십 초)
- 결과가 웹훅으로 나중에 오는 결제수단 (가상계좌 등)
- 결제 한 번에 여러 서비스를 차례로 부를 때 (쿠폰 · 포인트 등)
- 결제 중에도 같은 주문 행을 써야 하는 기능 (결제 대기 주문 취소 등)
- 결제가 순간적으로 몰려 파드당 커넥션 수에 닿을 때
- 내부 호출 응답 제한을 크게 늘릴 때
