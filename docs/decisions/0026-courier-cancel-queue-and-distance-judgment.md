# 0026. 택배 취소는 취소 대기를 먼저 기록하고, 큐가 택배사에 보내고, 택배사가 누른 시각의 기사 거리로 판정한다

> 상태: ✅ 확정 · 결정일 2026-11-17 · 결정한 사람: 배송 담당 (2026-11-16 ~ 17 설계 합의, #490)
> 대체: - · 대체됨: -

## 배경

택배 예약은 결제 커밋 직후 요청 스레드에서 택배사를 부르다가 세미 측정(#351)에서 커넥션 교착이 났고, 10초 택배 예약 큐로 바꿨습니다(#478). 취소는 아직 같은 구조입니다. 주문 트랜잭션 안에서 환불한 뒤 커밋 직후 택배사 취소를 부르므로, 택배사가 느리면 같은 교착이 나고, 택배사가 「이미 수거됨」이라고 해도 환불이 이미 끝나 있습니다.

또 취소와 수거가 거의 동시에 일어나면 누구 책임인지 정해야 했습니다. 기존 문서는 market이 수거 시각과 취소 요청 시각을 비교해 늦은 수거면 취소를 인정하고 반품을 자동 접수(왕복비 플랫폼)했습니다.

## 결정

1. **취소 대기 먼저 기록**: 구매자가 취소하면 배송을 `CANCEL_PENDING` + 누른 시각(`cancel_requested_at`)으로 조건부 UPDATE(`READY` · `BOOKED`일 때만)해 커밋하고 끝냅니다. 택배사는 부르지 않습니다. 같은 취소가 두 번 와도 한 번만 통과합니다.
2. **택배 취소 큐**: 10초 큐가 예약 큐와 같은 방식(한 건씩 `FOR UPDATE SKIP LOCKED` · 30초 임대 · 트랜잭션 밖 호출 · 10초 → 30초 → 1분, 끝까지)으로 택배사에 **주문번호(`courierOrderNo`) + 누른 시각**을 보냅니다. 택배사 결과를 배송 상태와 **결과 행(`SHIPMENT_CANCEL_RESULT`)** 하나로 같은 트랜잭션에 남깁니다.
3. **판정은 택배사**: 택배사는 누른 시각의 기사 거리로 판정합니다.
   - 2km 밖 → 취소. 2km 안 → 취소 불가(`CANCEL_LOCKED`, 409).
   - 2km 잠금 직후 30초 안에 누른 취소는 아직 수거 전이면 받아줍니다 (화면 갱신이 늦을 수 있어서).
   - 택배사 장애로 그사이 이미 수거됐는데 누른 시각엔 2km 밖이면 취소를 인정하고 **택배사가 반송**합니다 (택배사 비용, market은 새 배송 행을 만들지 않음).
   - 택배사에 예약이 없으면 「취소됨」을 기록해 두고, 늦게 온 같은 주문번호 예약을 받지 않습니다.
4. **환불은 주문 Saga**: 주문 Saga 복구가 결과 행을 읽어 취소됨이면 환불 → 주문상품 취소 완료 · 판매 재개, 취소 불가면 주문상품을 정상으로 되돌립니다.
5. **실패 원인 기록**: 예약 · 취소 큐 모두 마지막 실패 원인을 `last_error`에 남깁니다 (Outbox · 토큰 폐기 재처리와 같은 방식, [장애 처리](../conventions/resilience.md#결과-불명-처리)).

## 고른 이유

- 취소 API가 택배사를 기다리지 않아 커넥션을 쥐지 않습니다. 택배 예약 큐와 같은 원칙(임대 커밋 → 밖에서 호출 → 짧게 반영)입니다.
- 판정이 누른 시각 기준이라 큐 때문에 10초 늦게 도착해도 결과가 같습니다. 그래서 즉시 호출 없이 큐에만 맡깁니다.
- 동시성 판정을 택배사(서버 1대, 트랜잭션 하나) 한 곳에서 하므로 「취소됐는데 수거됨」이 생기지 않습니다. 2km 고지(배정 · 5km · 2km 알림, 주문 상세 문구)를 했으므로 2km 안 거절은 플랫폼 책임이 아닙니다.
- 환불을 택배사 결과 확정 뒤로 미뤄 「돈은 돌려줬는데 물건은 수거됨」을 막습니다.

## 다른 안

| 안 | 버린 이유 |
|---|---|
| 지금처럼 커밋 직후 요청 스레드에서 택배사 취소 | 세미 #351과 같은 커넥션 교착, 환불이 택배사 확인보다 먼저 |
| 취소 API에서 택배사를 바로 한 번 부르고 실패만 큐 | 주문 트랜잭션이 끝난 뒤(컨트롤러)에서 불러야 해 주문 코드 수정이 커짐. 누른 시각 판정이라 바로 부를 이득이 작음 |
| market이 수거 시각과 취소 시각을 비교해 판정 (기존 문서) | 택배사와 market의 시계가 다르고, 판정이 두 곳으로 나뉨. 반품 자동 접수 비용이 플랫폼에 남음 |
| 결과를 Spring 이벤트로만 주문에 전달 | 서버가 죽으면 사라짐. 결과 행은 DB에 남아 Saga가 다시 처리 |
| 실패 원인을 로그 · 트레이스로만 | Outbox · 토큰 폐기 재처리는 `last_error`를 남기고 있어 배송 큐만 달라짐 |
