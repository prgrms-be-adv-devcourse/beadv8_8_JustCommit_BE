# 타임아웃 · 재시도 · 서킷 브레이커

> 언제 읽나: 외부 호출이나 서비스 간 호출의 실패 처리를 정할 때
> 상태: ✅ 확정 · 마지막 수정 2026-11-08 · 관련: Miro 14, 노션 기획안 「장애 처리」

## 공통값

| 항목 | 값 |
|---|---|
| 라이브러리 | Resilience4j는 쓰지 않음 → [ADR 0011](../decisions/0011-no-circuit-breaker.md). 타임아웃은 HTTP 클라이언트 설정, 재시도는 `common-web` 그룹 설정기 |
| 내부 호출 `internal` | 연결 1초 · 응답 3초 |
| 재시도 | 연결 실패만 0.2초 쉬고 1번 (요청이 도착하지 않아 다시 보내도 안전). 503 · 응답 타임아웃 · 4xx는 재시도 안 함 |
| Gateway 기본 | 연결 1초 · 응답 10초, 재시도 없음 (POST 중복 방지) |
| Gateway 실패 응답 | 🟨 연결 불가 503(다시 시도 안전) · 응답 타임아웃 504(결과 불명, 프론트가 상태 조회) · 응답 중 끊김 502 · 그 밖의 에러 500 + 로그 — 공통 담당 회신 대기 |
| 업무 재시도 | 호출 한 번 안의 재시도가 끝난 뒤 「나중에 다시 하기」는 스케줄러가 맡음 → [스케줄러](../reference/schedulers.md) |

## 서킷 브레이커

**쓰지 않습니다** (Gateway 포함) → [ADR 0011](../decisions/0011-no-circuit-breaker.md)

- 서킷이 열리면 그 기능이 통째로 멈추고, 대비책이 또 필요하며, 실패를 일부러 일으켜 열 수도 있습니다.
- 대신 죽은 파드는 K3s readiness가 요청 분배에서 빼고, 모두 죽으면 연결이 바로 거절되어 Gateway가 503을 돌려줍니다.
- 오래 기다리는 문제는 타임아웃으로, 돈 · 상태는 결과 불명 처리로 막습니다.

## 결과 불명 처리

응답 타임아웃이 났다고 **바로 보상(되돌리기)하지 않습니다.** 상대가 처리했을 수도 있기 때문입니다.

1. 업무 상태는 도메인별 "진행 중" 상태 하나로 둡니다 (`PAYMENT_PENDING`, `CANCEL_PENDING` 등).
2. 원인은 `last_error` 칸에 남깁니다 (`TIMEOUT`, `CONNECTION_REFUSED` 등).
3. 스케줄러가 같은 멱등 키로 다시 요청하거나 결과를 조회합니다.
4. 실제로 실패한 것이 확인될 때만 보상합니다.
